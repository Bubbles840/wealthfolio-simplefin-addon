## #83: a sync wipes a cost basis entered by hand

**Report.** These are investment accounts whose institution sends no cost basis: a
deferred-comp plan and two 529s. The user enters the real cost in Wealthfolio. The next sync
saves a new holdings snapshot with every position at cost 0, and with the snapshot's
`cost_basis` and `net_contribution` at 0.
- The holdings then show "incomplete cost basis" again.
- The Net Worth page reads the drop in net contribution as a $100k withdrawal.

**How it works today.**
- Only the add-on writes snapshots, through `shared/sync-core.ts` (holdings pass, ~4945) →
  `src/utils/addon-host.ts` (~251) → `src/utils/holdings-prices.ts`
  `syncHoldingsWithFeedPrices`. The companion has no snapshot route.
- Since 1.75.0, a position the feed sends without a cost gets `carriedCost`
  (`shared/holdings.ts` ~187). That is the cost Wealthfolio already holds, read from
  `getHoldings`, which reads the latest snapshot.
- The carry is skipped for a holding on a **shared asset that is not MARKET-priced**
  (`holdings-prices.ts` ~348: `!own && sharedMode !== 'MARKET'`). The reason: Wealthfolio's import
  writes a MANUAL asset's average cost as that day's quote. See upstream
  `manual_snapshot_service.rs`, "Create a quote from the snapshot price as a fallback", which
  creates `YYYYMMDD_ASSETID` with close = avg cost.
- That skip is the most likely cause here: plan funds are typically on hand-priced shared
  assets. It is likely, not proven.
- **Net contribution is Wealthfolio's doing, not ours.** `ManualSnapshotService` sets
  `net_contribution` and `net_contribution_base` to `Decimal::ZERO` on **every** snapshot it saves,
  including Wealthfolio's own holdings editor. No input can carry a net contribution. So the only
  way to keep a hand-set figure is to not write a snapshot.

**Decided (Nick, A + B).**

### A. Don't write a snapshot when nothing changed
- After the import check has resolved asset ids, compare the snapshot about to be written
  (`written`) with what Wealthfolio holds now (the `getHoldings` read the sync already makes).
  Skip the import when all of these hold:
  - the same set of assets: every feed position is held, and no held non-cash position is
    missing from the feed. A position sold to 0 must be written;
  - each share count is exactly equal. Compare decimals, not floats. A number the read can't
    represent exactly counts as "different";
  - where SimpleFin sent a cost: Wealthfolio's total cost for the position is within $0.01 of
    SimpleFin's total. A carried cost is equal by construction;
  - the cash per currency is equal to the cent. Cash comes from the holdings read's cash lines;
    `HeldAsset` has no cash field today, so it must be added to the read. If cash can't be read,
    the snapshot is written;
  - no holding **changes asset** today. Careful: `moving` is NOT "moves today". It holds every
    holding on, or moving to, its per-account asset, rebuilt on every sync, so a description-named
    plan fund is in it every day. Only a real change of asset forces a write:
    - `firstMove`: the per-account asset doesn't exist yet;
    - `movedBack`;
    - a holding going from its shared asset onto a per-account asset that already exists.
    Comparing the written positions' asset ids with the held ones catches all of these. A
    holding staying on its per-account asset must NOT force a write, or A does nothing for the
    reporter's plan funds.
- Anything unreadable or ambiguous means **write, as today**. The skip must never be the risky
  branch.
- A skipped write counts in the outcome's `skipped` (no new field needed). Everything else in the
  pass still runs, above all step 5, which writes the feed's price on per-account assets. So
  values stay current, because prices are not carried by snapshots.
- The existing "a snapshot already exists for this date" skip is unchanged.
- **Dividends** (`shared/dividends.ts` `snapshotDatesToRead`) look only at snapshots in the 60
  days before a dividend. With sparse snapshots, a fund sold after a long quiet stretch could have
  no snapshot in that window that still holds it.
  - Add the snapshot in force at the window's start (the newest one on or before it) as a
    candidate. Lowest priority, within `SNAPSHOT_READS`.
  - The date listing must be able to reach it even when it is older than `SNAPSHOT_WINDOW_DAYS`.
    For example: list back up to 2 years, or list once more only when the window holds no
    snapshot. The builder picks whichever keeps the per-sync read cost bounded.
- Visible side effect (accepted): Wealthfolio's snapshot history gets a new entry only when
  something changed, not every day.

### B. Carry the cost onto hand-priced shared assets, then put the price back
- A position the feed sent without a cost, held on a shared asset whose mode Wealthfolio
  **reports as MANUAL**, now gets `carriedCost` exactly as a MARKET one does.
  - A mode the read doesn't report keeps today's behaviour: no carry, no restore. Plan review
    (my call): such an asset may be one the market prices, and writing a MANUAL quote there could
    replace the market's quote for the day. Wealthfolio 3.13's holdings read reports the mode, so
    current users lose nothing.
  - The same price restore also covers a position whose cost SimpleFin **did** send, when it sits
    on a shared asset reported as MANUAL. Today the import overwrites that day's price with the
    cost there too. The planner found this; it's pre-existing and the same mechanism fixes it.
  - Same carry rules as for MARKET:
  - shares the same or fewer: same average cost;
  - more shares: the new ones at the feed's price that day;
  - a change of 1.5× or more either way, or no usable price: ask, and write cost 0, as now.
- **Price restore.** Before the import, read the asset's price history:
  - If it has a quote dated the snapshot day, remember it exactly.
  - Otherwise remember the latest quote before that day.
  - With **no quote at all, don't carry** (today's behaviour). Otherwise the cost would become
    its price.
- After a successful import, write the remembered price back as that day's manual quote
  (`manualQuote`, same id, so it replaces the import's). Use the remembered quote's currency
  where it has one.
- If the restore fails, retry once. If it still fails, add a sync error naming the fund:
  "Couldn't put back the price of X after saving its holdings. It shows at its cost until its
  next price."
- The `kept` path already restores the last price before the day. Make it prefer a same-day
  quote the same way, so a price someone entered for that day survives too.
- Holdings the person priced by hand are otherwise untouched: no mode change, and no move to a
  per-account asset.

### Reply on #83 (drafted at the end; posted only with Nick's OK)
- The cost is kept now.
- Net contribution is reset by Wealthfolio itself on every holdings save, its own editor included.
  After this change that happens only on days the share counts change.
- If it still happens, tell us the funds' pricing mode.
- No upstream issue **(my call)**.

## #80: the Amazon fallback can't be a subcategory

**Today.** In `src/components/AmazonCard.tsx`, "Category for anything unrecognized" lists
top-level categories only (`options`). The comment there says this was a deliberate call: "a
broad category is the honest home". The companion already resolves the fallback with
`findAmazonCategory`, which reads `Parent / Child` paths (`companion/src/amazon-filing.ts` `idOf`,
since 1.74.0). In practice the fallback files mixed orders, and it's the preselected value for
labels with no rule.

**Decided (Nick).**
- The fallback dropdown offers the same list as the label rows (`labelOptions`):
  - subcategories as `Parent / Child`, behind `companionFilesAmazonSubcategories(companionVersion)`;
  - top-level only with a companion older than 1.74.0;
  - never the sync's bookkeeping categories.
- A stored value is shown the way the label rows show it: a legacy bare name as the option it
  files under, and the current value kept in the list even if it isn't an option. So leaving the
  dropdown alone never changes what is saved.
- Replace the "stays top-level" comment with the new reasoning.
- No change to the Telegram label picker (main categories only, by design).

## #79: fee reversals import as income

**Today** (`shared/mapper.ts` `mapTransactionWithSource`):
- A user rule wins first.
- On a card: money in is TRANSFER_IN when the text matches `CARD_PAYMENT_KEYWORDS`, otherwise
  CREDIT. So "LATE CHARGE ADJUSTMENT" is already a refund, but "LATE PAYMENT FEE REVERSAL" becomes
  a card payment.
- On cash: bank-transfer wording is TRANSFER_IN, and anything else coming in is DEPOSIT, which is
  income.
- On a CASH account, a CREDIT counts as spending only with subtype REFUND, REBATE or
  REIMBURSEMENT (`shared/cash-flow-bucket.ts`). A bare CREDIT is neutral.
- A re-sync recomputes the type and rewrites it (`shared/reconcile.ts` `changed()`), except
  create-only rule rows, kept paybacks and kept dividends.

**Decided (Nick, option 2: type plus the fee's category).**

### Type: in both hosts, shared code
- **Fee reversal**: money in (amount > 0) on a CASH or CREDIT_CARD account whose text has a
  **fee word** and a **reversal word**.
  - Fee words: `fee`/`fees` as whole words (so "COFFEE" never matches), `service charge`,
    `late charge`.
  - Reversal words: waived/waiver, reversal/reversed, refund/refunded, rebate,
    reimbursement, adjustment/adj, and "credit" **only directly after a fee word**
    ("LATE FEE CREDIT", "SERVICE CHARGE CREDIT"). Build review, my call: "ACH CREDIT" prefixes
    ordinary incoming deposits at many banks, so a bare "credit" would read "CONSULTING FEE ACH
    CREDIT" (income) as a refund.
  - The builder tunes the exact regex against a fixture list. It must cover at least:
    - matches: "Monthly Maintenance Fee Waived", "ADJUST FEE CHARGED ATM FEE REBATE",
      "LATE CHARGE ADJUSTMENT", "LATE PAYMENT FEE REVERSAL", "OVERDRAFT FEE REFUND",
      "ATM FEE REIMBURSEMENT", "SERVICE CHARGE REVERSAL";
    - non-matches: "TAX REFUND", "COFFEE REFUND", "AMAZON REFUND",
      "MONTHLY MAINTENANCE FEE" (no reversal word), and any outflow.
- Result: `CREDIT`, subtype `REFUND`, `fromRule: false`, plus a flag (e.g. `feeReversal: true`).
- Checked **after** the user rule and **before** the card-payment and bank-transfer keywords.
- Kept out of transfer pairing (`detectTransferPairs`) and learned transfer typing, through the
  flag or `fromRule`. A fee reversal must never be re-typed as a transfer half.
- A payback stays a payback. The `asReimbursement` override and `keepPayback` keep winning, and
  a stored CREDIT/REIMBURSEMENT is never turned into REFUND, so payback Undo keeps working.
- Never `REIMBURSEMENT`: that subtype means "payback" throughout.
- Existing DEPOSITs like this that are still in the fetch window get retyped on the next sync.
  The change log shows them as "Retyped" (existing behaviour).
- A person who disagrees adds a transaction rule; rules win.
- `shared/tx-story.ts`: give fee reversals a short "why" line (read as a refund of a bank fee from
  its wording), next to the REIMBURSEMENT one.
- **Two writers.** An older add-on or companion still maps these to DEPOSIT, so the two would
  retype the row back and forth until both are updated. Accepted: the release notes say to update
  both, and the existing version-skew warning covers it.

### Category: companion only (my call, reasoning given to Nick)
- Every automatic filing (Amazon, sync bookkeeping) lives in the companion, which can assign a
  category directly. The add-on can only file through a temporary rule plus `rerunRules`, which
  today runs only on a person's "It's a payback" tap.
- Add-on-only users get the type. Their category comes from Wealthfolio rules or from "Needs a
  category".
- **The pass** runs alongside the Amazon and bookkeeping filing, on the same read path (the
  mounted DB when available, as those do). For each fee-reversal CREDIT/REFUND row:
  - in the last 60 days, with **no spending category**;
  - find the **fee it reverses**: same account, money out, exactly the same amount, text with a
    fee word and no reversal word, dated 0–30 days before;
  - closest date first; one fee reverses at most one refund;
  - if that fee has a spending category, assign the same category to the refund.
- **Never** touch a row that already has a **spending (expense-kind)** category, whether from a
  person or a rule.
- **A leftover income category counts as none (builder-check answer, my call).** A fee reversal
  that came in as a DEPOSIT may already sit under an income-kind category (people file refunds
  under "Refunds"-style income categories; `incomeReimbursements` exists for that).
  - After the retype that category counts nowhere: Wealthfolio leaves assignments alone on
    `update_activity`, and the row stops being income.
  - So the pass treats an income-kind category on a fee-reversal refund as "no spending
    category", and files the row under the fee's category.
  - The change-log entry records the old category, so Undo puts it back. After Undo the row is
    never refiled.
  - With no fee found, the row keeps its old category. That's the person's to fix; the pass
    never clears a category.
- Record each filing in the change log with Undo, the way Amazon filings are recorded
  (`recordFiling`). An undone filing is not redone (Amazon's `noAutoFile` mechanism, or the same
  idea).
- Rows with no fee found are left alone. If uncategorised, they already raise the daily
  `idle-refund` finding, which is the right prompt.

### Reply on #79 (drafted at the end)
- What changed.
- An ATM rebate of another bank's fee often has no fee row to copy from, so a rule or a one-off
  pick files it.

## #81: stale institution data looks current (my call: report SimpleFin's errors everywhere)

**Findings.**
- **The live Bridge** (checked 2026-11-18 against the public demo,
  `https://demo:demo@beta-bridge.simplefin.org/simplefin`):
  - With **no version parameter** it answers protocol **v1**: `errors` (plain strings), and
    `org` on each account.
  - With **`version=2`** it answers `errlist` (structured: `code`, `msg`, `conn_id`,
    `account_id`) and `connections`, and each account carries `conn_id` with **no `org`**.
  - A connection: `{conn_id, name, org_id, org_name, org_url, sfin_url}`. The v1 `org.name`
    equals the v2 connection **`name`** ("SimpleFIN Demo"), not `org_name`.
- **Codes** (spec, https://www.simplefin.org/protocol.html): `con.auth` = a connection needs the user to sign
  in again; `con.` = a general connection error; `act.failed` and `act.missingdata` = an account
  read failed, "try again later"; `gen.auth`; `gen.api` = developer-only.
- **What we do today:**
  - We send no version, so we only ever get v1 strings. `normalizeAccountSet` already parses
    `errlist` if it comes.
  - Errors reach the Sync page only after a manual sync. Scheduled add-on syncs drop them.
  - The companion only logs them ("Sync note:"), and `/status` reports `synced`.
  - The account is processed as current.
  - The `feed-stale` self-check reads `balance-date`, which the Bridge keeps fresh, so it never
    fires.

**Decided (my call).**

1. **Ask for v2 from SimpleFIN Bridge only.**
   - Send `version=2` on `/accounts` when the access URL's host is a SimpleFIN Bridge host
     (`*.simplefin.org`), in both fetchers: `src/utils/simplefin.ts` and
     `companion/src/simplefin.ts`.
   - Lunch Flow and any other server keep today's request byte for byte. Lunch Flow's v2 support
     is unverified.
   - `normalizeAccountSet` fills each account's missing `org` from its connection:
     `name ← connection.name`, `domain ← host of org_url`, `url ← org_url`,
     `'sfin-url' ← sfin_url`. It also keeps `conn_id` on the account (add it to `SimplefinAccount`).
   - Everything downstream that reads `org` must see exactly what v1 gave, above all
     `accountNameWords` (`sync-core.ts` ~1636 / ~2707), whose words decide which descriptions
     name a connected account (transfer typing). Pin this with a test fed the real demo payloads
     (v1 and v2 of the same accounts) that gets the same org name and name words from both.
   - **Why `connection.name` and not `org_name`** (builder-check question, my call):
     - The live Bridge's own v1 `org.name` is the connection's `name` ("SimpleFIN Demo"), not
       `org_name` ("SimpleFIN Bridge"). The same server derives both, so this reproduces today's
       words exactly.
     - The spec's "My Bank - James" example is illustrative, not observed. If real connection names
       did carry a person's name, v1 `org.name` would already carry it today, so nothing changes.
     - Residual risk: the Bridge derives v1 `org.name` differently for real connections than for
       the demo. Cost if so: a connection-name word could start naming an account in transfer
       typing. Listed for Nick.
   - Error lines name the connection: `describeBridgeError` uses the connection name for a
     `conn_id` error.
2. **Remember the problems.**
   - A new store record, `simplefin_problems`: `{checkedAt, problems: [...]}`. Each problem is
     `{key, code, kind: 'signin' | 'other', connectionName?, sfinAccountIds, message,
     firstSeenAt, lastSeenAt}`.
   - Written by **every sync that got a 200 from `/accounts`**, in both hosts: read, merge, write,
     keeping `firstSeenAt` for keys still reported. A problem not reported this time is dropped,
     which is how it gets "fixed".
   - Follow the `unmapped_accounts` precedent: an optional store method that both stores
     implement.
   - `kind: 'signin'` for `con.auth` and `gen.auth`. Everything else is `other`, including legacy
     v1 strings (keyed by message).
   - Never kept: the existing window-size notices (`isSimplefinNotice`), `gen.api`, and problems
     whose known accounts are all unmapped or ignored.
   - `sfinAccountIds`: every account with that `conn_id` for a connection problem, or the one
     account for an account problem.
   - `message` is sanitised: plain text, length-capped. The spec requires sanitising anything
     shown.
3. **When a problem is shown.**
   - `signin` right away.
   - `other` only once it has lasted 24 hours (`firstSeenAt`), so "try again later" blips stay
     quiet.
   - The add-on ignores a record whose `checkedAt` is more than 48 hours old: the record would be
     stale itself, for example with an old companion and no recent add-on sync.
4. **Where it's shown.**
   - **Add-on Home:** a warning banner per shown problem, using the existing banner style. Sign-in
     wording, for example: "Fidelity NetBenefits needs you to sign in again at SimpleFIN Bridge.
     Until you do, its accounts show the last figures SimpleFIN got, not today's." Link to the
     Bridge site the access URL points at. Affected mapped accounts get a "not updating" mark in
     the account list.
   - **Telegram (companion):**
     - A one-time notice when a shown problem first appears, and one when it clears ("… is updating
       again"), with a ledger of announced keys like `announced_unmapped_accounts`.
     - A daily-report finding while it lasts: a `SelfCheckFinding` that prints in full and can be
       snoozed by key.
   - **Home Assistant** (builder-check answer). It's an alert channel beside Telegram, fed by both
     halves from the `SyncResult` (`shared/home-assistant.ts` `syncAlertEntries`), and it already
     carries new-account alerts.
     - Newly shown problems become HA alerts the same way: the `SyncResult` carries them, as it
       carries `unmappedAccounts`.
     - Each alert key includes the episode start (`firstSeenAt`), because HA ignores a repeated key
       for 30 days (`HA_SEEN_MAX_AGE_MS`). Otherwise a problem that clears and comes back within a
       month would never be announced.
     - No "updating again" alert in HA (it has no resolve concept). Telegram says it.
   - **`/status`:** a count of problems being shown, with no names (the page carries none).
   - The Sync page result keeps showing errors, now worded with the connection's name.
5. **Not doing.**
   - No "value hasn't moved for N days" guess. It would cry wolf on money market and stable-value
     funds (TSP G Fund), and the reporter's case is one SimpleFin does report. Revisit only if
     someone hits staleness SimpleFin doesn't report.
   - No holding back of an account's balance, prices or snapshot while it's broken. The last
     figures are all anyone has, and #83-A already stops writing unchanged snapshots.

**Version skew.** A new add-on with an old companion: the record comes only from add-on syncs,
and the 48-hour rule hides it once it goes stale. A new companion with an old add-on: Telegram and
`/status` work, and the add-on shows nothing new. No gate is needed.
